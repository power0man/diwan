# CI وبوابة الدفع وترحيل التوقيع — التنفيذ المصحّح

> سجل ترحيل تاريخي. ق٤٩ يحكم إعادة البناء الحالية ومراجعتها الآلية؛
> تصميم المشرف الدائم والعامل العابر في `../ci/README.md`، وحالة
> التفعيل وأدلته في `REBUILD-2026-09-23.md`. العبارات القديمة أدناه
> عن ق١٩، وغياب المشرف، والبوابات المعلقة لا تصف الحالة الحالية.

**الحالة في ٢١ سبتمبر ٢٠٢٦: التوقيع والبوابة مفعّلان؛ CI قيد الإثبات.**
فوّض المالك إنشاء الهوية وتسجيل الحاوية وحذف سر GitHub بعد نجاح CI.
أُنشئ المفتاح في Keychain، ونجحت قراءته الأصلية دون تعديل ACL.
رُحلت المراسي الخمس عشرة وحُفظت تواقيعها السابقة؛ لم تتغير بايتات
السجلات أو المراسي ولا الملفات الـ277 الأخرى في فحص المقارنة.
التحقق العام: 15/15 على الأصل و7/7 على النسخة المدفوعة بلا أي سر.
ثُبتت حزمة الثقة وhook في النسختين. بناء الصورتين ومجس runner نجحا؛
باقي الإغلاق المشروط هو CI الفعلي ثم حذف سر GitHub وفصل التسجيل القديم.

هذه الوثيقة تسجل تصحيح تنفيذ الأجزاء الثلاثة في
`TASK-CI-SIGNING.md` بعد مراجعة حدود الثقة. لا تفتح مرحلة جديدة ولا
تلغي ق١٩. القرارات الحاكمة: ق٣٦ وق٣٧ وق٣٨ في `DECISIONS.md`.
التفويض الصريح الحالي يشمل إنشاء مفتاح Keychain وتسجيل الحاوية
وحذف سر GitHub بعد النجاح؛ وفصل التسجيل القديم مفوض بشرط النجاح
أيضًا. الأوامر أدناه دليل إعادة الإجراء، وليست إذنًا بتغيير هوية قائمة
أو إنشاء خدمة دائمة جديدة. تثبيت hook قابل للإزالة من ضمن العمل.

## ١. الأجزاء الثلاثة بعد التصحيح

| الجزء | التنفيذ المعتمد | ما يصححه من وصف المهمة الأول |
|---|---|---|
| CI ذاتي | Linux ARM64 داخل حاوية جديدة لكل مهمة، بعلامة `diwan-isolated` | العودة إلى runner على حساب المالك لا تعزل Keychain؛ تشغيله في login session أو إفراغ env لا يصلح ذلك |
| بوابة الدفع | أداة موثوقة خارج الشجرة تفحص SHA كل مرجع يُدفع، ثم تنفذ فحوصه داخل runtime معزول بلا شبكة | لا تفحص `HEAD` بدل المدفوع، ولا تنفذ شيفرة المرشح على المضيف، ولا تستعمل `git archive` الذي قد يحذف ملفات عبر attributes، ولا تثبت حزمًا داخل البوابة |
| Ed25519 | خطة ترحيل معتمدة وتوقيع خاص عند المالك، ثم تحقق عام بسياسة ومفتاح مثبتين | غياب السر لا يكفي وحده لعزل العملية؛ وبعد التفعيل لا يقبل التحقق الصارم HMAC أو رمز الخروج 3 نجاحًا |

التشغيل الذاتي يزيل اعتماد مهمة الاختبار على دقائق GitHub المستضافة؛
لا يعني ذلك انعدام كلفة الجهاز أو الصيانة أو كل خدمات GitHub الأخرى.
الاعتمادية `cryptography` مثبتة ببصمات في `requirements-ci.lock`.
كل Python في الفحوص يأتي من runtime واحد مضبوط؛ لا اعتماد ضمني على
اسم `python3` أو Python النظام. غياب backend هو
`signing_backend_missing`، دون رجوع صامت إلى خوارزمية أضعف.

## ١.٥ لماذا لا يعمل CI؟ — تشخيصٌ قبل الانتظار

بتصميم ق٣٦ **لا مُشغِّل مقيمًا**: كلُّ مهمةٍ تحتاج حاويةً عابرة
يبدأها المالك، فالوصلةُ المدفوعة تبقى في الطابور **بلا حدٍّ زمني**
حتى تُشغَّل. هذا مقصود، لكنه كان **بلا أي إشارة** — لا رسالة ولا رمز
ولا موضع يُسأل، وهو خرقٌ لـ«لا مسار صامتًا». فأُضيف:

```bash
.venv/bin/python ci/ci_status.py \
  --runner-receipt ~/diwan-work/diwan-ci-trust/20260921-ed25519/runner.json
```

قراءةٌ وتشخيصٌ فقط — لا يبني صورةً ولا يسجّل مُشغِّلًا ولا يمسّ
حالةَ GitHub. يعيد أولَ مانعٍ يجده برمزه: `docker_unavailable`،
`runner_image_missing`، `no_runner_registered`، `queued_waiting`،
`idle`. ورمزُ خروجه غيرُ صفري عند مانعٍ يحتاج فعلًا.

**فائدةٌ مقيسة**: يوم ٢١ سبتمبر بقيت وصلةٌ في الطابور بلا سبب ظاهر،
وظُنَّ أن صورة المُشغِّل ضاعت — وكانت موجودةً كاملة **بلا وسم** فقط،
فغابت عن `docker images | grep diwan`. الفحصُ بالمعرّف لا بالقائمة
الموسومة يمنع تشخيص عطلٍ لا وجود له.

### الطقس بعد كل دفعة

١. `ci_status.py` — إن كان `no_runner_registered` فالمطلوب حاوية.
٢. **فعلُ المالك** (الرمزُ عبر أنبوب، لا في وسيط ولا بيئة ولا ملف):

```bash
gh api -X POST repos/power0man/diwan-private/actions/runners/registration-token --jq .token \
  | .venv/bin/python ci/start_isolated_runner.py \
      --runner-receipt ~/diwan-work/diwan-ci-trust/20260921-ed25519/runner.json \
      --repository https://github.com/power0man/diwan-private
```

٣. تلتقط الحاويةُ مهمةً واحدة ثم تزول ويُلغى تسجيلُها تلقائيًّا.

**وحدٌّ معلن**: البوابةُ المحلية قبل الدفع تشغّل **قائمة الفحوص
نفسها** (`tools/verification_checks.py`)، فـCI تأكيدٌ مستقل لا
المصدرُ الوحيد للثقة. وصلةٌ اجتازت البوابة ولم تُشغَّل لها حاوية
**ليست غيرَ مفحوصة** — هي غيرُ مؤكَّدة في بيئةٍ ثانية، وهذا فرقٌ
يجب ألا يُخلط.

## ٢. CI المعزول وحدوده

`verify.yml` يستهدف `[self-hosted, Linux, ARM64, diwan-isolated]` فقط.
الصلاحية `contents: read`، وcheckout مثبت بوصلة كاملة مع
`persist-credentials: false`. لا وظيفة أو خطوة تحمل HMAC أو مفتاح
Ed25519 الخاص. قائمة الفحوص الوحيدة هي
`tools/verification_checks.py`، ويشغّلها `tools/run_verification.py`:
pytest، اتساق الوثائق، قبول م٠ وم٨-ب وم٩ إلى م١٣، فحص JavaScript
وسلوك الواجهة، م٧، ثم `sign_anchors.py verify --public-only` الصارم.

صورة runtime تضم Python 3.14 وNode 24 والاعتماديات المثبتة، ولا تضم
تطبيق runner أو بيانات المشروع أو مفاتيحه. صورة runner مستقلة فوقها.
البناء يستعمل صور أساس رسمية مثبتة بـdigest، وسياقًا محدودًا إلى
Dockerfile وlock وملف bootstrap اللازم. الإيصال يحفظ **Docker image
Id القياسي** بعد `inspect`؛ فقد يكون IID الذي يعيده BuildKit من نوع
manifest/index مختلف. يستخدم بناء runner وسمًا محليًا مشتقًا من
هوية runtime الكاملة، ويرفض التصادم ويتحقق من الهدف قبل البناء وبعده.

`start_isolated_runner.py` ينشئ حاوية بلا ربط لأي مسار من المضيف:
لا HOME المالك، ولا Keychain، ولا socket Docker، ولا ملف `.env`.
تعمل بمعرف مستخدم غير root، وقدرات مسقطة، و`no-new-privileges`، وجذر
للقراءة فقط، وtmpfs للعمل والمنزل والملفات المؤقتة. رمز التسجيل يدخل
عبر stdin ثم بيئة عملية الإعداد المؤقتة داخل الحاوية؛ لا يمر في argv
المضيف أو إعداد Docker أو ملف. بيانات اعتماد runner التي تنشأ أثناء
التسجيل تبقى في tmpfs ثم تزول مع الحاوية.

`--ephemeral` يحد المهمة بواحدة ويلغي التسجيل بعد معالجتها؛ **لا
يعزل المضيف ولا يمسح قرصه بذاته**. bootstrap يزيل الحاوية عند الخروج
أو المهلة أو المقاطعة، ويعلن الفشل إذا تعذر إثبات الإزالة. لا توجد
حلقة تسجيل دائمة ولا خدمة مثبتة. انقطاع المضيف قد يترك تسجيلًا
متوقفًا يحتاج تنظيف المالك. تعطيل التحديث الآلي يتطلب إعادة بناء
صورة runner المراجعة عند تحديثاته ضمن مهلة GitHub.

الحاوية تشارك نواة بيئة Docker، وCI يحتاج شبكة GitHub؛ لا تدعي هذه
الدفعة منع كل وصول إلى خدمات المضيف المتاحة شبكيًا أو مقاومة اختراق
النواة. عند اشتراط هذا الحد يلزم جهاز/VM مخصص وعابر وسياسة خروج
شبكية. بوابة الدفع المحلية، بخلاف CI، تعمل بـ`--network=none`.
لا تدعم الصورة container actions أو service containers بلا daemon.

وجود runner القديم مسجّلًا يبقي إمكانية اختياره من workflow آخر.
لا يُمنح القديم علامة `diwan-isolated`، ولا يُعلن إغلاق هذا المنفذ
حتى يفصل المالك تسجيله ويتحقق من الحالة الفعلية.

## ٣. بوابة الدفع: ما تفحصه وما لا تضمنه

يفهم `pre-push` أسطر stdin ويثبت OID المدفوع لكل مرجع، بما فيها
الوسوم التي تشير إلى commit. اختلاف SHA المدفوع عن `HEAD` لا يغيّر
هدف الفحص. حذف مرجع مرفوض في المسار العادي، والكائن الذي لا يشير
إلى commit مرفوض. الفشل في أي مرجع يمنع الدفعة.

تستخرج الأداة blobs الخام إلى لقطة مؤقتة مستقلة، دون hooks أو
filters أو hardlinks. الروابط الرمزية وgitlinks وتعارضات الأسماء
والمسارات مرفوضة. يتحقق كود موثوق من التواقيع العامة **قبل** تنفيذ
شيفرة المرشح؛ لا يستورد verifier من تلك اللقطة. ثم تشغّل الفحوص
داخل حاويات runtime مثبتة الهوية، بلا شبكة، مع ربط اللقطة المؤقتة
وحدها. لا pip ولا مفاتيح ولا شيفرة مرشح على مضيف المالك.

الإيصال الخارجي يربط هوية الصورة ونسخة Python وNode وبصمة lock
وبصمة ملف الثقة الخارجي. لا يكفي label الصورة: مجس موثوق بلا ربط
المرشح يثبت versions وملف lock وإصدارات توزيعاته. اختلاف lock في
مرشح جديد يحتاج إعداد cache جديدًا ومراجعًا، ولا يسمح بتنزيل تلقائي.
المجلدات الموثوقة بصلاحية 700 وملفات إعدادها 600، خارج كل worktrees
للمستودع. `install_hooks.py` ينسخ حزمة تحقق موثوقة مستقلة ويحفظ hook
السابق ويستدعيه؛ وعند الإزالة لا يستبدل ملفًا تغيّر خارج ملكيته.

غياب المخازن المحلية الاختيارية بالكامل في لقطة Git يعلن تخطيًا،
ولا يُنشئ ملفات بدلها. وجود جزء من ثلاثية السجل/المرساة/التوقيع
يفشل؛ ولا يعفى سجل إلزامي أو تيار موجود لعقدة جديدة من التحقق.
صحة نسخة المالك المحلية فحص منفصل عبر `--owner-health`، وليست بديلًا
عن فحص commit المدفوع. هذا الفحص الاختياري يستعمل جرد المالك الحالي؛
توسع الجرد يحتاج تحديث عقده بدل إخفاء الفرق.

م٧ يقرأ خطة الحقوق والمصادر والإسقاط القائم دون بناء أو لمس البيان.
البناء واللقطات وتوقيع HMAC الاختباري على بيانات مؤقتة فقط، مع حجب
تحميل مفاتيح الإنتاج منذ بداية القبول. حالة HMAC القديمة غير القابلة
للتحقق تظهر صراحة أثناء القراءة؛ البوابة النهائية لا تقبلها نجاحًا.
أدلة م٤/م٥/م٦ الحية وقياس جودة الإجابة ليست جزءًا من هذه البوابة.

`pre-push` يعمل بعد بدء اتصال Git بالبعيد؛ يمنع إرسال التحديثات
عند الفشل، ولا يصح وصفه بأنه «قبل أي شبكة». الأداة نفسها لا تحتاج
شبكة للفحوص. `DIWAN_SKIP_GATE=1` تجاوز صريح مطبوع في JSON؛ لا يلغي
hook السابق. `git push --no-verify` يتجاوز hook كليًا، فلا يستطيع
hook تسجيل ذلك أو منعه. لا تدعي البوابة مصادقة المالك أو فرض سياسة
غير قابلة للتجاوز، ولا تحوّل اختبارات الشيفرة إلى حكم جودة للنموذج.
زمن الرزمة الكاملة في الحاوية يُقاس قبل تقرير صلاحيتها لكل دفعة؛
لا تُختلق مدة ولا يُضاف وضع سريع يسقط تحققًا صامتًا.

## ٤. الترحيل إلى Ed25519

المفتاح العام raw32 في `keys/anchor-ed25519.pub`، والسياسة القانونية
في `keys/anchor-policy.json`، وبصمتها مثبتة في
`core.signing.PINNED_POLICY_SHA256`. ملف عام مجاور وحده لا ينشئ ثقة:
تبديل المفتاح والسياسة معًا يجب أن يفشل أمام pin المراجع، وبوابة
الدفع تحمل نسخة موثوقة مستقلة منهما. المفتاح الخاص seed مستقل في
Keychain تحت الخدمة `diwan-anchor-ed25519`؛ ليس مشتقًا من مفتاح HMAC.
التحقق العام لا يستدعي أي محمّل مفتاح خاص.

الخطة تشمل الأجيال التاريخية المدوّرة، وترفض تاريخًا ناقصًا قبل قراءة
أي سر. وتربط الجذر ومجموعة السجلات وبصمات بايتات كل سجل ومرساة وتوقيع
قديم وبصمة المفتاح العام الجديد. `plan` لا يثبت صلاحية HMAC من دون
مفتاحه؛ `apply` يتحقق من **كل** التواقيع القديمة ومطابقة المفتاح
الجديد قبل أول تحويل، وتحت أقفال الكتابة. `--resign` إقرار بتحويل
الخوارزمية، وليس إذنًا بتجاوز HMAC مخالف أو إصلاح سلسلة فاسدة.

تبقى بايتات السجلات والمراسي كما هي، وتحفظ التواقيع السابقة في
`var/signature-migration/<plan-sha256>/` بصلاحيات خاصة. استبدال كل
توقيع ذري، لكن المجموعة ليست معاملة واحدة؛ الاستئناف يستعمل **الخطة
نفسها والبصمة نفسها**، ويتحقق من المكتمل ونسخه السابقة. لا يُنشأ
plan جديد لإخفاء انقطاع غير مفهوم. توقف الكتابة والتشغيل الاعتيادي
طوال الترحيل؛ قد توجد صيغتان في وسط العملية، ولا يعلن حينها نجاح
سياسة Ed فقط. تُفعّل السياسة وpin بعد اكتمال التحويل ومراجعته.

بعد التفعيل، التوقيع المتوقع للسجلات الحاكمة هو Ed25519؛ HMAC فيها
رفض، حتى مع بقاء سره متاحًا. تبقى قراءة التاريخ HMAC وظيفة صريحة
ضمن نطاقها القديم، ولا تكون fallback للتحقق العام. كل append محكوم
أو تدوير أو بناء نشر لسجل موقّع يحتاج قدرة التوقيع قبل الكتابة.

الترحيل يعتمد الحالة الحالية المتحقق منها، ولا يثبت بأثر رجعي
أصالة مادة كانت غير موقعة. إعادة ثلاثية قديمة صحيحة كاملة خارج
كشف التوقيع وحده؛ شاهد الزمن الخارجي موضوع مستقل. كذلك لا يحمي
Ed25519 مفتاحه إذا شغلت شيفرة غير موثوقة على UID المالك نفسه.

## ٥. أوامر المالك وتسلسل التفعيل

ينفذ المالك هذه الخطوات بعد مراجعة الشيفرة وفي نافذة كتابة متوقفة.
كل القيم بين الأقواس مسارات أو بصمات يحددها المالك، وليست أوامر
جاهزة للتنفيذ الجماعي. لا تُسجل أسرار أو رموز في shell history، ولا
يُفعّل `set -x`. نسخة الأدوات الموثوقة خارج الشجرة المرشحة؛ أما
أداتا إنشاء المفتاح والترحيل فتعملان من نسخة المالك للمستودع المعني،
لأن خطة الترحيل مرتبطة بجذرها.

### أ. إعداد runtime المالك والمجلد الخاص

```bash
DIWAN_REPO='/absolute/path/to/owner-checkout'
DIWAN_TRUSTED_SOURCE='/absolute/path/to/reviewed-tool-copy'
DIWAN_STATE='/absolute/path/outside/all-worktrees/diwan-ci-state'
DIWAN_REPOSITORY='OWNER/diwan'
umask 077
mkdir -p "$DIWAN_STATE"
chmod 700 "$DIWAN_STATE"
python3.14 -m venv "$DIWAN_STATE/owner-venv"
DIWAN_PYTHON="$DIWAN_STATE/owner-venv/bin/python"
"$DIWAN_PYTHON" -m pip install --require-hashes -r "$DIWAN_REPO/requirements-ci.lock"
"$DIWAN_PYTHON" -m pip check
cd "$DIWAN_REPO"
```

هذا تثبيت اعتماديات صريح في مرحلة الإعداد؛ لا تعيده البوابة عند
الدفع. يعتمد Python 3.14 فعليًا؛ اسم الأمر وحده ليس إثبات النسخة.

### ب. إنشاء الهوية الجديدة وخطة التحويل

```bash
"$DIWAN_PYTHON" tools/anchor_keys.py create \
  --public-output "$DIWAN_STATE/anchor-ed25519.pub"
```

ينشئ هذا الأمر المفتاح الخاص في Keychain دون إخراجه إلى argv أو
ملف، ويكتب العام فقط. يرفض استبدال مفتاح أو وجهة قائمة. إذا اكتمل
إنشاء المفتاح وانقطع تصدير العام، يستعمل المالك `export` إلى وجهة
جديدة بدل محاولة إنشاء هوية أخرى:

```bash
"$DIWAN_PYTHON" tools/anchor_keys.py export \
  --public-output "$DIWAN_STATE/anchor-ed25519-recovered.pub"
```

راجع بصمة العام المطبوعة، ثم استخدم مسار العام الذي اعتمدته فعلًا:

```bash
DIWAN_PUBLIC_SHA256='<reviewed-public-key-sha256>'
"$DIWAN_PYTHON" tools/migrate_ed25519.py plan \
  --public-key "$DIWAN_STATE/anchor-ed25519.pub" \
  --fingerprint "$DIWAN_PUBLIC_SHA256" \
  --output "$DIWAN_STATE/ed25519-plan.json"
```

راجع الخطة كاملة وبصمتها وجردها. تبقى القدرة على قراءة مفتاح HMAC
القديم مطلوبة للتحقق وقت `apply`؛ لا يُحذف مفتاحه من Keychain أولًا.
التطبيق إقرار منفصل وصريح:

```bash
DIWAN_PLAN_SHA256='<reviewed-plan-sha256>'
"$DIWAN_PYTHON" tools/migrate_ed25519.py apply \
  --plan "$DIWAN_STATE/ed25519-plan.json" \
  --sha256 "$DIWAN_PLAN_SHA256" --resign
```

عند انقطاع معروف، أعد الأمر نفسه بعد مراجعة الحالة. لا تستعمل
إعادة التوقيع العامة أو تعدّل خطة قديمة لإسكات رفض.

### ج. تثبيت السياسة العامة بعد التحويل

بعد نجاح التحويل ومراجعة سلامة جميع السجلات، انسخ **العام فقط**
إلى المسار الثابت دون استبدال ملف قائم، وأنشئ سياسة canonical من
`policy_document` و`canonical_policy_bytes`. احسب SHA-256 لبايتاتها
وثبّته بمراجعة شيفرة في `PINNED_POLICY_SHA256`. هذه خطوة تفعيل
مقصودة؛ أداة الترحيل لا تعدّل pin تلقائيًا. لا تُفعل السياسة قبل
التحويل ولا تُدفع وصلة تحمل حالة مختلطة.

يمكن للمالك إعداد الملفات العامة وملف الثقة الخارجي التالي بعد
اعتماد العام؛ يعرض بصمة السياسة العامة فقط، ولا يقرأ مفتاحًا خاصًا:

```bash
"$DIWAN_PYTHON" - "$DIWAN_STATE" <<'PY'
import hashlib, json, os, sys
from pathlib import Path
from core.signing import policy_document, canonical_policy_bytes
state = Path(sys.argv[1])
public = (state / 'anchor-ed25519.pub').read_bytes()
raw = canonical_policy_bytes(policy_document(public))
policy_hash = hashlib.sha256(raw).hexdigest()
Path('keys').mkdir(exist_ok=True)
for path, data in ((Path('keys/anchor-ed25519.pub'), public),
                   (Path('keys/anchor-policy.json'), raw)):
    with path.open('xb') as handle:
        handle.write(data)
trust = {'schema_version': 1, 'algorithm': 'ED25519',
         'public_key_hex': public.hex(), 'policy_sha256': policy_hash}
fd = os.open(state / 'trust.json', os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600)
with os.fdopen(fd, 'w') as handle:
    json.dump(trust, handle, sort_keys=True)
    handle.write('\n')
print('policy_sha256=' + policy_hash)
PY
```

بعد تثبيت البصمة المطبوعة في الشيفرة، أعد تجهيز نسخة الأدوات
الموثوقة لتشمل **pin نفسه**، ثم تحقق قراءةً:

```bash
"$DIWAN_PYTHON" tools/sign_anchors.py verify --public-only
```

النتيجة المطلوبة رمز 0 وتواقيع Ed متحققة لكل الموجود، مع تخطي الغياب
المحلي المسموح وحده. لا تُفسّر رفض legacy قبل هذه الخطوة عطلًا يجب
تحويله إلى نجاح؛ إنه حاجز التفعيل المقصود.

### د. بناء cache الصور وربطها بالثقة المعتمدة

في أمثلة الصور التالية يحل المالك محل `<reviewed-digest>` digest
رسميًا راجعه وقت الإعداد، ولا يحذف جزء `@sha256:`:

```bash
"$DIWAN_PYTHON" "$DIWAN_TRUSTED_SOURCE/ci/prepare_runtime.py" \
  --python-image 'python:3.14-slim-bookworm@sha256:<reviewed-digest>' \
  --node-image 'node:24-bookworm-slim@sha256:<reviewed-digest>' \
  --lock "$DIWAN_REPO/requirements-ci.lock" \
  --trust-json "$DIWAN_STATE/trust.json" \
  --receipt "$DIWAN_STATE/runtime.json" \
  --runner-receipt "$DIWAN_STATE/runner.json"
```

استخدم builder محليًا يرى Docker image store. الإيصالات لا تُستبدل
تلقائيًا؛ عند تحديث lock أو الثقة أو الصور أنشئ مجموعة جديدة مراجعة.
الوسم المحلي وسيط بناء فقط؛ التنفيذ والبوابة يستعملان image Id ثابتًا.

### هـ. فحص وصلة صريحة وتثبيت hook

الأداة الموثوقة تحتاج core وtools المراجعين مع pin المعتمد، لا نسخ
ملف `verify_gate.py` منفردًا. حدّد SHA كاملًا لوصلة تحتوي الترحيل
والسياسة المراجعين؛ لا يستنتج الأمر هدفه من `HEAD`:

```bash
DIWAN_COMMIT='<full-reviewed-commit-sha>'
"$DIWAN_PYTHON" -I "$DIWAN_TRUSTED_SOURCE/tools/verify_gate.py" \
  --repo "$DIWAN_REPO" --commit "$DIWAN_COMMIT" \
  --runtime "$DIWAN_STATE/runtime.json" --trust "$DIWAN_STATE/trust.json"
"$DIWAN_PYTHON" "$DIWAN_TRUSTED_SOURCE/tools/install_hooks.py" \
  --repo "$DIWAN_REPO" --state-dir "$DIWAN_STATE/hooks" \
  --runtime "$DIWAN_STATE/runtime.json" --trust "$DIWAN_STATE/trust.json" \
  --python "$DIWAN_PYTHON"
```

لفحص جرد نسخة المالك أيضًا أضف `--owner-health "$DIWAN_REPO"` إلى
أمر البوابة؛ لا يغني ذلك عن فحص الوصلة. إزالة hook الذي ثبتته الأداة
تعيد السابق إذا بقيت بصماته كما هي:

```bash
"$DIWAN_PYTHON" "$DIWAN_TRUSTED_SOURCE/tools/install_hooks.py" \
  --repo "$DIWAN_REPO" --state-dir "$DIWAN_STATE/hooks" --uninstall
```

### و. تسجيل مهمة CI واحدة وتنظيف الاعتماد السابق — بيد المالك

بعد اعتماد الصورة والسياسة ووصول الوصلة المقصودة إلى `main`، تحقق
من وجود مهمة `verify` في الانتظار؛ دفع `main` ينشئها عادة. إذا لم
توجد مهمة منتظرة، يطلبها المالك صراحة ثم يشغّل الحاوية:

```bash
gh workflow run verify.yml --repo "$DIWAN_REPOSITORY" --ref main
```

مرّر رمز تسجيل جديد مباشرة إلى stdin. الأمر الآتي **يسجّل runner
فعليًا**؛ لا يدخل في اختبار آلي أو hook، ويظل في الطرفية حتى تنتهي
المهمة الواحدة أو المهلة:

```bash
set +x
set -o pipefail
gh api --method POST "repos/$DIWAN_REPOSITORY/actions/runners/registration-token" \
  --jq .token |
  "$DIWAN_PYTHON" "$DIWAN_TRUSTED_SOURCE/ci/start_isolated_runner.py" \
    --runner-receipt "$DIWAN_STATE/runner.json" \
    --repository "https://github.com/$DIWAN_REPOSITORY" --timeout 3600
```

يتوقف launcher بعد مهمة واحدة أو المهلة؛ يحتاج التشغيل اللاحق إقرار
مالك ورمزًا جديدًا، لا حلقة تحتفظ بـPAT. يبدأ المالك التشغيل المطلوب
على الوصلة المعتمدة ويتحقق من نتيجة `verify` على `main` نفسه.

الفصل من GitHub ليس حذفًا لخدمة المضيف أو ملف بيئته. بعد مراجعة
هوية runner القديم وحالته ومنع تعطيل مهمة جارية، يفصل المالك
التسجيل المحدد فقط. لا يغيّر هذا خدمات الماك أو ملف بيئته القديم؛
إزالة البقايا المحلية قرار صيانة مستقل. مفتاح Ed الخاص لم يدخل ذلك الملف.
لا يُكتب معرف runner حقيقي في هذه الوثيقة:

```bash
DIWAN_OLD_RUNNER_ID='<reviewed-old-runner-id>'
gh api --method DELETE "repos/$DIWAN_REPOSITORY/actions/runners/$DIWAN_OLD_RUNNER_ID"
gh secret delete DIWAN_ANCHOR_KEY --repo "$DIWAN_REPOSITORY"
gh secret list --repo "$DIWAN_REPOSITORY"
gh run list --repo "$DIWAN_REPOSITORY" --workflow verify.yml --branch main --limit 5
```

هذه أعمال مالك دائمة، لا تنفذها البوابة ولا CI ولا وثيقة الشرح.
التحقق الأخير يستعمل أسماء الأسرار وحالات التشغيل، لا قيم الأسرار.
لا يُحذف مفتاح HMAC التاريخي أو نسخه اللازمة للتحقيق ضمن هذه الخطوة.

## ٦. دليل الإغلاق المطلوب

لا يُعلن الإغلاق الكامل إلا بعد حفظ دليل
ترحيل المالك والتحقق العام الصارم، وفحص الوصلة المدفوعة في runtime
المعزول، ومجس دفع أحمر محلي مصطنع يمنع التحديث، ونجاح CI على آخر
`main`، والتحقق من غياب سر HMAC وفصل runner القديم. يبقى تثبيت hook
وتشغيله الفعلي مختلفين عن اختبار المُثبّت في مستودع مؤقت.

لا يغلق ذلك قبول الجودة العربية أو بنك التقييم أو الحقوق أو النشر
الخارجي. لا يجيز المستودع الخاص مشاركة مادة لم تحسم حقوق توزيعها،
ولا تعالج هذه الدفعة تاريخ Git القديم بإعادة كتابة قسرية.
