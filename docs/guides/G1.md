# G1 — حماية الفرع main وقواعد الدمج في مستودع power0man/diwan (المهمة ح١)

**الهدف:** بعد هذا الدليل لا يدخل شيءٌ إلى main إلا بطلب دمجٍ (Pull Request) نجح فيه فحص verify-hosted على آخر إيداع، والفرعُ محدَّثٌ على main، والدمجُ بإيداع دمج (merge commit) فقط لا squash ولا rebase، ولا دفعَ قسريًّا ولا حذفَ للفرع، والدمجُ الآليّ (auto-merge) مفعَّل، وتحكم main منظومةُ حمايةٍ واحدة (Ruleset) بدل اثنتين. هذا يحوّل قاعدة «منجز = دُمج بطلبٍ بإيداع دمج والفحوص خضراء» (docs/PROJECT-PLAN-20260925.md §٦) من أمانةٍ مكتوبة إلى قيدٍ تفرضه GitHub، ويحمي حرّاس البصمات (tests/test_task_table_hashes_exist.py وtests/test_tasks_ledger.py وtools/issue_ledger.py) التي تشترط أن تكون بصمةُ كل مهمّةٍ منجزة وإيداعُ دمج كل طلبٍ سلفًا حقيقيًّا لـ main (كلُّها تنفّذ git merge-base --is-ancestor). يُغلق ح١، ويفتح الطريق لـ ح٤ (تثبيت مراجع من عائلة أخرى ثم طلب family-review إلزاميًّا = G2)، ويُنجز الشطرَ الثاني من ك٣٠ (حماية main بطلب دمجٍ أخضر)، ويجعل الدمج الآليّ ممكنًا لك٦ وما بعدها. الحالة اليوم كما قرأتُها من واجهة GitHub العامة (api.github.com) في ٢٦ سبتمبر ٢٠٢٦: لا Ruleset على المستودع (القائمة فارغة)، لكن على main حمايةٌ كلاسيكية قائمة (branch protection rule: protected=true، تشترط فحص verify من GitHub Actions، وتُطبَّق على الجميع بمن فيهم المدير)، وطرق الدمج الثلاث كلُّها مسموحة، وauto-merge معطَّل، وAllow update branch معطَّل. فالدليل ينشئ الـ Ruleset ثم يُنهي الحمايةَ الكلاسيكية القديمة حتى لا تتراكب منظومتان (GitHub تطبّق الاثنتين معًا وتأخذ الأشدّ).

**الزمن:** ١٥–٢٥ دقيقة للخطوات ١–١٥ في الواجهة، و٥ دقائق للخطوة ١٦ (قراءة القاعدة الكلاسيكية ثم حذفها)، بشرط أن يكون Claude قد دمج تعديل الاسم verify-hosted قبلها (نحو ٢٠ دقيقة من عمله مع تشغيل الفحص). الخطوة ١٧ دقيقتان بعد G2. الخطوة ١٩ تنتظر اكتمال فحص verify-hosted على طلبٍ واحد (نحو ٥–١٠ دقائق). · **الكلفة:** $0 لمرّة واحدة و$0 شهريًّا: الـ Rulesets وauto-merge وحماية الفروع ميزاتٌ أصلية في GitHub للمستودعات العامة، وverify-hosted يعمل على مشغّل GitHub المستضاف بدقائق مجانية غير محدودة للمستودع العام (كما تقول ترويسة .github/workflows/verify-hosted.yml). لا عتاد ولا خدمة ولا مفتاح.

## قبل أن تبدأ

- أنت مسجَّل الدخول إلى GitHub بحساب power0man (مالك المستودع؛ الإعدادات لا تظهر لغيره). المستودع مملوكٌ لحسابٍ شخصي لا لمنظّمة، فبعض الخيارات (مثل وضع Evaluate في الـ Ruleset) لن تظهر، وهذا طبيعي.
- المستودع عام (visibility=public، private=false؛ تحقّقتُ من api.github.com في ٢٦ سبتمبر ٢٠٢٦) فمهمّة verify-hosted تعمل آليًّا على كل طلب دمج بلا دقائق مدفوعة.
- شرط تقني يقوم به Claude لا أنت (اطلبه منه قبل البدء بجملة واحدة: «أضف name: verify-hosted تحت jobs.verify في .github/workflows/verify-hosted.yml وافتح طلب دمج وادمجه»). السبب: اليوم اسمُ الفحص الذي تنتجه مهمّة verify-hosted.yml هو verify (المهمّة معرّفها jobs.verify في السطر ٢٠ بلا name)، وهو نفسُ اسم فحص verify.yml الذي يُتخطّى (skipped) في المستودع العام؛ وتحقّقتُ من ذلك على رأس الطلب #121: يظهر فحصان باسم verify أحدهما skipped والآخر success. والمتخطّى بشرط if يُبلَّغ Success حسب وثائق GitHub. تسميةُ المهمّة verify-hosted تعطيها اسمًا فريدًا يُطلب في الحماية بلا لبس. الملف .github/ في مسار anthropic (registry/lanes.json) فلا يحتاج Claude سطر «تسليم:». وبعد دمج ذلك التعديل يجب أن يعمل الفحص باسمه الجديد مرّةً واحدة على الأقل (على طلب الدمج نفسه أو على الدفع إلى main بعد دمجه) حتى يظهر في قائمة الفحوص عند الخطوة ١٢، لأن GitHub لا يعرض إلا فحوصًا اكتملت بنجاح في المستودع خلال آخر ٧ أيام (وثائق GitHub: Troubleshooting required status checks).
- قرارٌ منك قبل الخطوة ١٢: هل تجعل فحص family-review إلزاميًّا الآن؟ هو اليوم يفشل بالتصميم على كل طلب (تحقّقتُ: failure على رأس #121، وهو المصمَّم في .github/workflows/family-review.yml ومعرّف مهمّته family-review فاسم الفحص family-review) لأنه لا يوجد بعد تطبيقُ مراجعٍ محتسَب من عائلةٍ أخرى (registry/reviewers.json يحتسب gemini-code-assist[bot] وchatgpt-codex-connector[bot] وclaude[bot] فقط، ولا يحتسب github-actions[bot]). فإن طلبته الآن لن يُدمج أيُّ طلبٍ آليًّا حتى ينجز الدليل G2، ويبقى دمجُك اليدوي بالتجاوز ممكنًا. التوصية: لا تطلبه الآن، وأضفه بعد G2 (الخطوة ١٧).
- لا حاجة إلى أي سرٍّ أو مفتاح؛ كل الخطوات في واجهة GitHub، وأوامر التحقق تقرأ الواجهة العامة بلا توكن (باستثناء تفاصيل الحماية الكلاسيكية التي لا يقرؤها إلا المالك من الواجهة).
- على الماك: نسخة العمل محدَّثة (git pull origin main) وpytest مثبَّت (uv sync --frozen --extra dev) لتشغيل حرّاس البصمات في التحقق الأخير.

## الخطوات

### 1. المتصفح: https://github.com/power0man/diwan/settings (أو من صفحة المستودع: التبويب Settings؛ وإن لم يظهر فمن قائمة «…» ثم Settings)

### 2. Settings → General → قسم Pull Requests

أبقِ Allow merge commits مفعَّلة. ألغِ تفعيل Allow squash merging وألغِ تفعيل Allow rebase merging. لا تغيّر القائمة المنسدلة لنصّ الرسالة تحت Allow merge commits (الافتراضي Default message مناسب لأن حارس النسبة يعفي إيداع الدمج الخالي من محتوى).

**ما تتوقّع أن ترى:** خانة واحدة مفعَّلة فقط: Allow merge commits. تُحفظ هذه الخانات فورًا عند النقر (لا زرّ Save لهذا القسم؛ إن ظهر زرّ حفظ فاضغطه).

> لماذا إيداع الدمج وحده: (أ) tests/test_task_table_hashes_exist.py يشترط أن تكون بصمةُ كل مهمّةٍ «منجزة» في AGENTS.md §٣ إيداعًا تصل إليه HEAD (git merge-base --is-ancestor)، وtools/issue_ledger.py يشترط أن يكون إيداعُ دمج الطلب (merge_commit_sha) سلفًا لـ main، وtests/test_tasks_ledger.py يفحص docs/TASKS.jsonl بالشرط نفسه؛ وsquash وrebase يُنشئان إيداعاتٍ جديدة ببصماتٍ مختلفة فتصير البصماتُ المكتوبة غير موجودة على main ويسقط الحرّاس. (ب) tools/agent_attribution.py يطلب ذيل Diwan-Agent في كل إيداعٍ غير دمجٍ (ويفحص إيداع الدمج فقط إن حمل محتوًى)، ورسالةُ squash الافتراضية لطلبٍ فيه إيداعان فأكثر هي عنوان الطلب وقائمة عناوين الإيداعات (وثائق GitHub، Configuring commit squashing) فيضيع الذيل ويُردّ الإيداع. (ج) tools/lane_handoff.py يقرأ سطر «تسليم:» من رسالة كل إيداعٍ أصليّ، وsquash يدمج الرسائل فيلتبس. وهذا ما نصّت عليه docs/PROJECT-PLAN-20260925.md §٠ («حارسُ البصمات يشترط أن يكون الإيداع سلفًا لـ HEAD، فالدمجُ يكون بإيداع دمج فقط، لا squash») و§٦. والتاريخ الحالي لـ main كلُّه إيداعات دمج فعلًا (Merge pull request #121 و#119…).

### 4. Settings → General → قسم Pull Requests (نفس القسم، نحو أسفله)

**ما تتوقّع أن ترى:** الخانة مفعَّلة. (اليوم allow_auto_merge=false حسب api.github.com.) لن ترى زرّ Enable auto-merge على طلب الدمج إلا حين يمنع قيدٌ الدمجَ الفوري (وهو قائم أصلًا بالحماية الكلاسيكية اليوم، وسيبقى بالـ Ruleset).

### 5. Settings → في الشريط الجانبي الأيسر تحت العنوان Code and automation → Rules → Rulesets (الرابط المباشر: https://github.com/power0man/diwan/settings/rules)

افتح صفحة Rulesets.

**ما تتوقّع أن ترى:** صفحة فارغة تقول إنه لا rulesets في المستودع (تحقّقتُ من api.github.com: /rulesets يعيد [] و/rules/branches/main يعيد [])، وفيها زرّ أخضر New ruleset.

> نصّ الوثائق الحالي (data/reusables/repositories/repo-rulesets-settings.md في github/docs): «In the left sidebar, under Code and automation, click Rulesets, then click Rulesets»؛ في بعض الواجهات يظهر العنصر باسم Rules ثم تحته Rulesets. المهم أن تصل إلى الصفحة التي فيها الزرّ New ruleset. تنبيه: فراغُ هذه الصفحة لا يعني أن main بلا حماية؛ الحماية الكلاسيكية القائمة تظهر في صفحةٍ أخرى (Settings → Branches) وستعالجها الخطوة ١٦.

### 6. صفحة Rulesets → الزرّ New ruleset

اضغط New ruleset ثم من القائمة المنسدلة اختر New branch ruleset (لا New tag ruleset).

**ما تتوقّع أن ترى:** تفتح صفحة إنشاء ruleset جديد وفيها الحقول: Ruleset name، وEnforcement status، وBypass list، وTarget branches، وBranch protections (قائمة قواعد بخانات اختيار).

> وثائق GitHub (create-ruleset-step): «Click New ruleset. To create a ruleset targeting branches, click New branch ruleset».

### 7. صفحة الـ ruleset الجديد → أعلى الصفحة

في حقل Ruleset name اكتب: protect-main . ثم بجانبه زرّ Enforcement status يظهر افتراضيًّا بقيمة Disabled؛ اضغطه واختر Active.

**ما تتوقّع أن ترى:** الاسم protect-main مكتوب، وزرّ الحالة يعرض Active (أيقونة تشغيل). Active يعني أن القواعد تُفرض فور الضغط على Create. (خيار Evaluate لا يظهر في المستودعات الشخصية؛ هو لخطط Enterprise.)

> وثائق GitHub (rulesets-general-step وrulesets-about-enforcement-statuses): «click Disabled and select an enforcement status»؛ «Active: your ruleset will be enforced upon creation».

### 8. صفحة الـ ruleset → قسم Bypass list

اضغط + Add bypass. في نافذة Add bypass التي تظهر ابحث عن Repository admin (ستراه في قسم Suggestions تحت الأدوار) واختره ثم اضغط Add Selected. بعد إضافته يظهر في القائمة وبجانبه Always allow؛ اضغط زرّ «…» على يمينه واختر For pull requests only.

**ما تتوقّع أن ترى:** صف واحد في Bypass list: Repository admin — For pull requests only. معناه: لا أحد، ولا حتى حساب المالك، يستطيع الدفع مباشرةً إلى main أو حذفَه أو دفعَه قسريًّا؛ لكن المالك يستطيع دمج طلبٍ لم تكتمل فحوصه (يظهر له في صندوق الدمج خيار تجاوز القواعد).

> وثائق GitHub (rulesets-bypass-step): «click + Add bypass … search for the role … select from the Suggestions section and click Add Selected»؛ و(rulesets-branch-tag-bypass-optional-step): «to the right of Always allow, click …, then click For pull requests only. The selected actor is now required to open a pull request … The actor can then choose to bypass any branch protections and merge that pull request». سبب اختيار For pull requests only بدل Always allow: كل الذكاءات (Claude على الماك وفي السحابة، وCodex، وGemini) تدفع بحساب المالك نفسه (registry/reviewers.json، وسطر lanes.json «the_agent_is_the_self_declared_Diwan-Agent_trailer_not_the_git_author»)، فتجاوزٌ مطلق للمالك هو تجاوزٌ مطلق لكل عميل، ويعود الدفع المباشر إلى main. أما قصرُ التجاوز على طلبات الدمج فيُبقي أثرًا لكل تغيير في طلب. الطوارئ: تدمج بنفسك من صفحة الطلب.

### 9. صفحة الـ ruleset → قسم Target branches

اضغط Add a target ثم اختر Include default branch.

**ما تتوقّع أن ترى:** يظهر هدف واحد: Default branch (وهو main؛ default_branch=main حسب api.github.com). لا تضف أنماطًا أخرى.

> وثائق GitHub (rulesets-target-branches): «select Add a target, then select how you want to include or exclude branches … For example, you could include the default branch».

### 10. صفحة الـ ruleset → قسم Branch protections (قائمة الخانات)

اضبط الخانات هكذا بالترتيب: (١) Restrict creations: اتركها غير مفعَّلة. (٢) Restrict updates: غير مفعَّلة. (٣) Restrict deletions: مفعَّلة (هي مفعَّلة افتراضيًّا؛ تأكّد). (٤) Require linear history: غير مفعَّلة — لا تفعّلها أبدًا، فهي تمنع إيداعات الدمج التي نشترطها. (٥) Require merge queue: غير مفعَّلة. (٦) Require deployments to succeed: غير مفعَّلة. (٧) Require signed commits: غير مفعَّلة (الذكاءات لا توقّع إيداعاتها بمفاتيح GPG، فتفعيلُها يوقف كل شيء). (٨) Require a pull request before merging: فعّلها — وستفتح تحتها Additional settings في الخطوة التالية. (٩) Require status checks to pass before merging: فعّلها — إعداداتها في الخطوة ١٢. (١٠) Block force pushes: مفعَّلة (افتراضيًّا؛ تأكّد). (١١) Require code scanning results وما بعدها: غير مفعَّلة.

**ما تتوقّع أن ترى:** أربع خانات مفعَّلة فقط: Restrict deletions، وRequire a pull request before merging، وRequire status checks to pass before merging، وBlock force pushes.

> وثائق GitHub (Available rules for rulesets): «Restrict deletions … This rule is selected by default»، «Block force pushes … This rule is enabled by default»، «Require linear history … prevents collaborators from pushing merge commits».

### 11. صفحة الـ ruleset → تحت Require a pull request before merging → Additional settings

اضبط: Required approvals = 0 (صفر؛ لأن حساب المالك هو الحساب الوحيد الذي يستطيع الموافقة، وكل الذكاءات تكتب به فلا معنى لموافقةٍ منه، والمراجعة من عائلةٍ أخرى يفرضها فحص family-review لا الموافقات). Dismiss stale pull request approvals when new commits are pushed: غير مفعَّلة. Require review from Code Owners: غير مفعَّلة. Require approval of the most recent reviewable push: غير مفعَّلة. Require conversation resolution before merging: غير مفعَّلة. ثم في إعداد طرق الدمج المسموحة (يظهر باسم Allowed merge methods أو قريبٍ منه وفيه ثلاث خانات: Merge وSquash وRebase): أبقِ Merge مفعَّلة وألغِ Squash وألغِ Rebase.

**ما تتوقّع أن ترى:** Required approvals تساوي 0، وكل الخانات الفرعية غير مفعَّلة، وطريقة الدمج الوحيدة المسموحة Merge.

> وثائق GitHub (Available rules for rulesets → Require a pull request before merging): «you can require a merge type of merge, squash, or rebase … if the repository has disabled a merge method and the ruleset required a different method, the merge will be blocked». وقد عطّلتَ squash وrebase على مستوى المستودع في الخطوة ٢ وتُبقي Merge هنا، فالقيدان متوافقان.

### 12. صفحة الـ ruleset → تحت Require status checks to pass before merging → Additional settings

فعّل خانة Require branches to be up to date before merging. اترك Do not require status checks on creation غير مفعَّلة إن ظهرت. ثم في حقل إضافة الفحوص (صندوق بحث) اكتب: verify-hosted واختره من القائمة ثم اضغط زرّ + (Add selected status checks). سيظهر صف verify-hosted وبجانبه عمود المصدر؛ اختر فيه GitHub Actions إن أتاحته الواجهة، وإلا اتركه Any source.

**ما تتوقّع أن ترى:** صف فحص واحد إلزامي: verify-hosted (المصدر GitHub Actions)، وخانة up to date مفعَّلة.

> وثائق GitHub (rulesets-protections-step): «You can enter the name of each status check … you must click + (Add selected status checks). If you select Require branches to be up to date before merging, you must define a check»؛ و(troubleshooting-rules): «Workflow: The name format is <job name>». اليوم، قبل تنفيذ الشرط المسبق الثالث، الاسم هو verify لأن المهمّة في .github/workflows/verify-hosted.yml معرّفها jobs.verify بلا name، وكذلك مهمّة verify.yml التي تُتخطّى في المستودع العام (if: github.event.repository.private)؛ وشاهدتُ الاسمين معًا على رأس #121. فإن لم يُدمج تعديل Claude بعد، اكتب verify بدل verify-hosted، واعلم أن GitHub يعدّ المهمّة المتخطّاة بشرط ناجحة (وثائق Troubleshooting required status checks: «A job is skipped by a conditional → The job reports Success»؛ «Successful check statuses are success, skipped, and neutral»)، ولم أستطع التحقق كيف يحكم GitHub حين يحمل فحصان الاسمَ نفسه أحدهما متخطًّى والآخر حقيقي (الوثيقة تغطي حالة check وcommit status بالاسم نفسه فقط: «both must pass»)؛ فالأسلم إتمام الشرط المسبق أولًا. ولا تضف family-review هنا الآن (انظر الخطوة ١٧). وإن لم يظهر verify-hosted في القائمة فلأنه لم يكتمل بنجاح بهذا الاسم خلال ٧ أيام؛ يمكنك كتابة الاسم يدويًّا في الصندوق ثم +.

### 13. صفحة الـ ruleset → أسفل الصفحة

اضغط الزرّ الأخضر Create.

**ما تتوقّع أن ترى:** تعود إلى صفحة Rulesets وفيها صف protect-main بحالة Active. من هذه اللحظة يفرض الـ Ruleset قواعده على main (بالإضافة إلى الحماية الكلاسيكية القديمة حتى تُزال في الخطوة ١٦؛ GitHub تطبّق الاثنتين وتأخذ الأشدّ).

### 14. Terminal على الماك (أو أي جهاز متصل بالإنترنت؛ لا حاجة إلى توكن)

نفّذ الأمر التالي كاملًا: curl -sS -H "Accept: application/vnd.github+json" https://api.github.com/repos/power0man/diwan/rules/branches/main

**ما تتوقّع أن ترى:** يطبع قائمة JSON فيها كائنات type بالقيم: deletion، وnon_fast_forward، وpull_request (وفي parameters: allowed_merge_methods تحوي merge فقط وrequired_approving_review_count تساوي 0)، وrequired_status_checks (وفيه strict_required_status_checks_policy: true وcontext: verify-hosted). إن طُبعت قائمة فارغة [] فالـ ruleset لم يُنشأ أو ليس Active أو لا يستهدف main.

> هذا الأمر يعرض قواعد الـ Rulesets وحدها، ولا يعرض الحماية الكلاسيكية (لذلك كان يعيد [] اليوم رغم وجودها).

### 15. Terminal على الماك

نفّذ: curl -sS -H "Accept: application/vnd.github+json" https://api.github.com/repos/power0man/diwan | grep -E '"allow_(merge_commit|squash_merge|rebase_merge|auto_merge|update_branch)"'

**ما تتوقّع أن ترى:** خمسة أسطر: allow_merge_commit: true، وallow_squash_merge: false، وallow_rebase_merge: false، وallow_auto_merge: true، وallow_update_branch: true. أيُّ قيمةٍ مخالفة تعني أن خانةً في الخطوات ٢–٤ لم تُحفظ.

### 16. Settings → في الشريط الجانبي تحت Code and automation → Branches (الرابط المباشر: https://github.com/power0man/diwan/settings/branches)

تحت Branch protection rules ترى قاعدةً قائمة لنمط main. اضغط Edit بجانبها واقرأ إعداداتها أولًا (المتوقّع: Require status checks to pass before merging مفعَّلة والفحص المطلوب verify، وDo not allow bypassing the above settings مفعَّلة؛ وقد تجد خانات أخرى لم أستطع قراءتها من الواجهة العامة). تأكّد أن كل ما فيها يغطّيه الـ Ruleset الذي أنشأته (طلب دمج، فحص إلزامي، منع الدفع القسري والحذف). ثم عد إلى القائمة واضغط Delete بجانب القاعدة وأكّد الحذف.

**ما تتوقّع أن ترى:** قسم Branch protection rules فارغ، وصفحة Rulesets تعرض protect-main وحده Active. الآن منظومةُ حمايةٍ واحدة تحكم main.

> لماذا: الحماية الكلاسيكية القائمة تشترط فحصًا اسمه verify (تحقّقتُ: required_status_checks.contexts=["verify"] وenforcement_level=everyone من api.github.com)، وبعد إعادة تسمية المهمّة لن يبقى تحت اسم verify إلا مهمّة verify.yml المتخطّاة في المستودع العام، فيصير شرطُ verify شرطًا يمرّ دائمًا بلا فحصٍ حقيقي وراءه، ويبقى القيدان متراكبين (وثائق About rulesets → About rule layering: «Rulesets and branch protection rules … work alongside each other, and all applicable rules are enforced … the most restrictive version applies»). إن فضّلت الإبقاء عليها فبدّل فيها الفحص المطلوب من verify إلى verify-hosted بدل الحذف. الحذف قرارُك أنت (AGENTS.md §٥ يمنع العميل من حذف ما لم يُنشئه، ولا يمنعك). وثائق GitHub (Managing a branch protection rule → Deleting): «To the right of the branch protection rule you want to delete, click Delete».

### 17. لاحقًا، بعد إنجاز الدليل G2 (تثبيت مراجعٍ محتسَب من عائلةٍ أخرى، وأن يمرّ family-review أخضر على طلبٍ واحد على الأقل): Settings → Rules → Rulesets → protect-main → Edit

في قسم Require status checks to pass before merging أضف فحصًا ثانيًا باسم family-review (اختره من القائمة ثم +) ثم اضغط Save changes أسفل الصفحة.

**ما تتوقّع أن ترى:** صفّان إلزاميان: verify-hosted وfamily-review. من هذه اللحظة يُدمج الطلب آليًّا فقط إذا راجعه بوتٌ من عائلةٍ غير عائلة مؤلّفيه (ق٦١).

> اسم الفحص family-review مؤكَّد من معرّف المهمّة jobs.family-review في .github/workflows/family-review.yml ومن رأس #121. إن أضفته قبل G2 فسيبقى كل طلبٍ أحمر ولا يدمج شيءٌ إلا بتجاوزك اليدوي من صندوق الدمج.

### 18. لا مكان — قرار: لا تُنشئ ملف CODEOWNERS

لا تضف ملف .github/CODEOWNERS (لا يوجد اليوم؛ تحقّقتُ في نسخة العمل وعبر api.github.com: 404). السبب المكتوب في tools/lane_handoff.py: «ملفُّ CODEOWNERS لا يخدم هذا لأن العملاء كلَّهم يدفعون بحساب GitHub واحد؛ فالعميلُ هو ذيلُ Diwan-Agent لا مؤلّفُ git». وregistry/lanes.json يُفرض بالفعل آليًّا بخطوة Touching another lane declares a hand-off في verify-hosted.yml وverify.yml، فسطر «تسليم:» صار فحصًا لا طلبَ مراجعة. ولو أُنشئ CODEOWNERS يربط المسارات بك، فلن ينفع إلا مع خانة Require review from Code Owners، وهي تجعل موافقتك اليدوية شرطًا لكل دمج، فتلغي الدمج الآليّ الذي تبنيه هنا، وتعطي «موافقةً» لحسابٍ يكتب به كل الذكاءات (reviewers.json: «the_owner_overrides_by_merging_himself_not_by_a_review»).

**ما تتوقّع أن ترى:** لا ملف CODEOWNERS في المستودع، ومسارات العائلات تبقى محكومة بـ registry/lanes.json وفحص lane_handoff.

### 19. تجربة حيّة: أوّل طلب دمجٍ يفتحه أيُّ ذكاءٍ بعد الإنشاء (أو اطلب من Claude فتح طلبٍ تجريبي بتغيير سطرٍ في docs/STATUS.md)

افتح صفحة الطلب وانظر صندوق الدمج أسفله. ثم اضغط Enable auto-merge واختر Create a merge commit وأكّد.

**ما تتوقّع أن ترى:** قبل اكتمال الفحوص يقول الصندوق إن الدمج محجوب حتى ينجح verify-hosted، ويظهر زرّ Enable auto-merge، وقائمة طريقة الدمج لا تعرض إلا Create a merge commit (لا Squash and merge ولا Rebase and merge). بعد نجاح الفحص يُدمج الطلب وحده بإيداع دمج، وتراه في سجل main بعنوان يبدأ بـ Merge pull request #<الرقم>. وإن تخلّف الفرع عن main يظهر زرّ Update branch فاضغطه (أو يضغطه الذكاء) ويُعاد الفحص.

> وثائق GitHub (Automatically merging a pull request): «Click Enable auto-merge»؛ و(Merging a pull request): «click the merge dropdown menu and select Create a merge commit».

## احذر

- ازدواج اسم الفحص verify: على كل طلبٍ اليوم فحصان باسم verify (تحقّقتُ على رأس #121: أحدهما skipped من verify.yml والآخر success من verify-hosted.yml)، والمتخطّى بشرط يُبلَّغ Success حسب وثائق GitHub. لم أستطع التحقق من حكم GitHub حين يجتمع الاسمان (هل يكفي أحدهما؟). وهذا العيب قائمٌ اليوم في الحماية الكلاسيكية نفسها التي تشترط verify. العلاج: name: verify-hosted في الـ workflow ثم طلب هذا الاسم، وإزالة القاعدة الكلاسيكية (الخطوة ١٦).
- الحماية الكلاسيكية القائمة لم أقرأ تفاصيلها كلَّها (واجهة API العامة تردّ 403 على /branches/main/protection بلا توكن؛ المؤكَّد: فحص verify إلزامي وتُطبَّق على الجميع). فاقرأها أنت في الخطوة ١٦ قبل حذفها؛ وإن حوت شيئًا لا يغطّيه الـ Ruleset فأضفه إليه أولًا.
- الوثيقة الحاكمة docs/PROJECT-PLAN-20260925.md §٣ و§٦ تسمّي الفحص الإلزامي verify-hosted، بينما الاسم الفعلي المنتَج اليوم verify؛ الشرط المسبق يزيل هذا التناقض، وإلا تبقى الوثيقة تصف اسمًا لا يظهر في الواجهة.
- طلب family-review الآن يجمّد الدمج الآليّ كليًّا حتى G2، لأنه يفشل بالتصميم على كل طلب (لا مراجعٌ محتسَب مثبَّت؛ تحقّقتُ: failure على #121)؛ ويبقى دمجك اليدوي بالتجاوز فقط، فتعود الأمانة بدل الآلية.
- التجاوز ممنوح لدور Repository admin، وكل الذكاءات تدفع بحساب المالك، فأيُّ ذكاءٍ يستطيع نظريًّا تعديل الـ ruleset نفسه أو الدمج بالتجاوز من صندوق الطلب؛ الحماية تمنع الدفع الصامت إلى main لا الإرادة. الحدّ نفسه معلَن في docs/PROJECT-PLAN-20260925.md §٩ عن أسرار CI.
- AGENTS.md §٥ (نسخة main الحالية) يقول بالفعل «ادفع فرعك وافتح طلب الدمج إلى main؛ فـmain محميٌّ بفحص verify»، لكنه يسمّي الفحص verify؛ بعد إعادة التسمية يُحدَّث إلى verify-hosted (مهمّة توثيق صغيرة لأي عميل، لا للمالك). وأي نسخة عملٍ قديمة على الماك ما زال فيها «ادفع إلى main» تحتاج git pull.
- Require branches to be up to date يعني أن كل طلبٍ يتأخر عن main يحتاج Update branch وإعادة تشغيل الفحص (نحو ٥–١٠ دقائق لكل مرّة على مشغّل GitHub المستضاف)؛ مع طلباتٍ متزامنة كثيرة يتحوّل هذا إلى طابور. البديل المستقبلي merge queue لكنه يتطلب حدث merge_group في الـ workflows ولم يُهيَّأ (لا ذكر له في .github/).
- إن فعّلت Require linear history أو Require signed commits بالخطأ فسيتوقف الدمج كليًّا (الأولى تمنع إيداعات الدمج، والثانية تطلب توقيعات GPG لا تملكها الذكاءات).
- الطلبات القادمة من Dependabot أو أي بوت لا يكتب ذيل Diwan-Agent ستفشل في verify-hosted كما هو مقصود (الخطة §٣)، وتحتاج دمجَ عميلٍ يعيد الإيداع بذيل.
- أسماء الأزرار والحقول قد تتغير في واجهة GitHub؛ ما تحقّقتُ منه من مصدر وثائق GitHub (github/docs، فرع main، ٢٦ سبتمبر ٢٠٢٦) مذكورٌ في الخطوات، وما لم أتحقق منه في uncertain_steps.
