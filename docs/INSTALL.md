# تثبيت ديوان (ج٦، #36)

## أمر مستقلّ

من نسخة المستودع العام على macOS:

```sh
uv tool install --python 3.12 .
diwan camel-data -i morphology-db-msa-r13
ollama pull qwen3.5:9b
diwan check
diwan serve
```

على Linux وWSL2 يكون أمر التثبيت:

```sh
uv tool install --python 3.12 --with 'torch==2.14.0+cpu' --find-links https://download.pytorch.org/whl/cpu/torch/ .
```

ويقبل التثبيت من Git مباشرةً: استبدل النقطة بـ`git+https://github.com/power0man/diwan.git`.
يُفضَّل تثبيت إصدار أو بصمة محدّدة بإضافة `@<ref>`. لا يُنشر شيء إلى PyPI بهذه الخطوة.
`uv tool install` يحلّ اعتماديات الحزمة، ولا يطبّق `uv.lock` ولا إعداد مصدر torch في المشروع؛ لذلك
تُذكر عجلة torch للمعالج ومصدرها صراحةً على لينكس، وتبقى بقية الحزم من PyPI. للتركيب المقفول استعمل
`uv sync --frozen` أو صورة Docker.
يلزم أن يكون مجلّد أدوات uv في PATH (`uv tool update-shell` ثم افتح طرفية جديدة).

`diwan serve --help` يعرض خيارات الواجهة نفسها، ومنها `--root` و`--runtime-receipt` و`--analysis-receipt`.
التشغيل من الحزمة يحفظ الحالة في `$DIWAN_DATA_HOME/daily-ui` إذا ضُبط المتغيّر، وإلا في
`$XDG_DATA_HOME/diwan/daily-ui` أو `~/.local/share/diwan/daily-ui`. لا تكتب الحالة في بيئة uv، فتبقى بعد الترقية.
مسارات التشغيل من الشيفرة (`tools/serve_ui.py`) باقية بإعداداتها السابقة.

الواجهة على `http://127.0.0.1:8765`. لا يبدأ نداء نموذج ولا تنزيله بأمر التثبيت.
قاعدة CAMeL والمحرّك متطلبان منفصلان. وPDF يحتاج **LibreOffice** محليًا؛ غيابه رفض مسمّى في أداة التصدير،
ولا يُثبَّت تلقائيًا. Windows عبر **WSL2**؛ الحزمة تعتمد على أدوات Unix ولا تعد بتشغيل Windows الأصلي.

## الحاوية

```sh
docker build -t diwan .
docker run --rm --network none diwan
```

فحص الحاوية يعمل بالأمر المثبَّت `diwan check`: رمز 0 يعني اكتمال خطوات الجهاز، و3 تعذّرًا معلنًا، و1 عطبًا.
بلا شبكة ولا متون يكون 3 متوقّعًا: CAMeL حاضر، والحلقة تعمل بمزوّد مكتوب سلفًا، وOllama والمتن غائبان.
تحقّق CI من هذه الحالات ينتهي بنجاح، دون تحويل تقرير الجهاز إلى «جاهز».

الحالة في الحجم `/app/var` والمستخدم غير الجذر. الصورة تحتوي أدوات الاختبار وNode وGit لتشغيل مجموعة
pytest نفسها في CI، ولا تحتوي متون المالك أو مفاتيحه. الحزمة تستخدم قائمة تضمين للشيفرة والموارد العامة
في `pyproject.toml`؛ لا تدخلها المحادثات ولا المتون ولا المفاتيح الخاصة، سواء كانت wheel أو sdist.

### الواجهة على Docker Desktop أو Linux

المزوّد المحلي يشترط loopback؛ لا نغيّر حكم الخصوصية لكي يصل إلى عنوان المضيف. يمكن تشغيل Ollama في
حاوية مصاحبة تشارك ديوان مساحة الشبكة، فيبقى عند `127.0.0.1:11434`. هذا طريق CPU على Docker Desktop؛
قد يكون التشغيل الأصلي على الماك أسرع، خصوصًا مع Metal. تنزيل النموذج خطوة صريحة:

```sh
docker run -d --name diwan-model -p 127.0.0.1:8765:8765 -v diwan-models:/root/.ollama ollama/ollama
docker exec diwan-model ollama pull qwen3.5:9b
docker run --rm --network container:diwan-model -v diwan-data:/app/var diwan diwan serve --listen 0.0.0.0
```

يُنشر المنفذ على `127.0.0.1` وحده، ويكون المنفذ الداخلي والخارجي 8765. الخيار `--listen` يغيّر عنوان
الاستماع فقط؛ فحصا Host وOrigin والرمز المحلي باقيان. لا يُنشر المنفذ على الشبكة العامة.
إعادة تشغيل حاوية ديوان مع `diwan-data` نفسه تعيد المشروعات والمحادثات؛ إزالة الحجم تحذفها.
أدوات تنفيذ Docker داخل المحادثة تحتاج إيصالها وبيئتها الخاصة؛ لا نربط مقبس المضيف بالصورة.

## ما يختبره CI

- بناء الصورة من `uv.lock`، ثم فحص الأمر المثبَّت بلا شبكة مع فحص كل حالة متوقّعة.
- pytest داخل Python 3.12، مع تاريخ Git للقراءة وحدها لاختبارات البصمات.
- كتابة محادثة مصطنعة، وإزالة الحاوية، وقراءتها من حاوية ثانية بالحجم نفسه.
- `uv tool install` في بيئة جديدة، ثم `diwan serve --help` و`diwan check` من خارج المستودع.
- بناء wheel وsdist وفي شجرة البناء ملفات خاصة مصطنعة: يجب ألّا تدخل أيًا منهما.

اختبارات الحزمة والحاوية لا تقيس جودة المحرّك، ولا تستبدل أدلّة ج٥ الحيّة.
فحص `container-smoke` يُشغَّل على كل طلب دمج بلا مرشّح مسارات؛ جعله شرط حماية للفرع من إعدادات المالك.
