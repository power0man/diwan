# RuFlo لتنسيق الأعمال المساعدة

يُستخدم [RuFlo](https://github.com/ruvnet/ruflo) سجلًا مساعدًا لتنسيق مهام تطوير ديوان المحدودة.
يبقى GitHub مرجع المسائل وطلبات الدمج، وتبقى `AGENTS.md` و`docs/VISION.md` حاكمتين على أدوار العملاء
والنطاق والمراجعة. لا تغيّر هذه الوصفة محرّك ديوان الافتراضي، ولا تضيف منفّذًا إلى المنتج.

## فصل المسؤوليات

| المكوّن | مسؤوليته |
|---|---|
| العميل المسجّل في ديوان | اختيار المهمة، وضبط الصلاحيات، والتحقق من النتيجة، والتحديث في GitHub |
| RuFlo | تتبع الحالة والإسناد والتبعيات؛ حفظ حالة المهمة لا يثبت إنجازها |
| Ollama، إن اختير نموذج محلي | اقتراح ناتج محدود قابل للتحقق؛ ليس مراجعًا مستقلًا بمجرد اختلاف الأداة |
| GitHub | المسألة الأصلية، والفرق القابل للمراجعة، ودليل القبول والإغلاق |

من المهام المناسبة للتجربة: تحويل قائمة عامة إلى JSON معلوم، واقتراح حالات حافة مصطنعة، وصياغة أسماء اختبارات.
تبقى المخرجات مقترحات غير معتمدة حتى يفحصها العميل، وتظل قاعدة اختلاف عائلة المراجع سارية.

## دورة مهمة محدودة

١. اقرأ تعريفات الأدوات المتاحة في نسخة RuFlo المستخدمة. افحص وجود بطاقة تطابق مرجع GitHub قبل إنشاء أخرى؛
لا تغيّر بطاقة تخص عملًا آخر، ولا تُعدّ غياب النتيجة من قائمة مبتورة إثباتًا لغيابها.

٢. أنشئ البطاقة بـ`task_create`، واجعل وصفها يحمل مرجع المهمة والمنسّق ومعيار القبول وحد الإنفاق والتبعيات.
ابدأ بحالة معلقة، وأبقِ العمل المعطّل بسبب تبعية غير منجز. أسماء الأدوات قد تحمل بادئة بحسب عميل MCP؛
استعمل الاسم الكامل من تعريف الأداة المتصل، ولا تفترض ثبات البادئة.

٣. عند تنفيذ تجربة بنموذج، أرسل تكليفًا عامًا صغيرًا مستقلًا عن ملفات المالك وبنوك القياس المحجوبة.
حدّد نموذجًا واحدًا، وحدًا للمخرج، ومهلة، وعدد محاولات معلومًا. لا تمنح النموذج أدوات أو صلاحية ملفات
إذا كان المطلوب اقتراحًا نصيًا فقط. لا حاجة إلى تهيئة المشروع كاملة أو تعديل `CLAUDE.md` أو hooks لتتبع بطاقة.

٤. تحقّق من اكتمال استجابة النموذج قبل فحص محتواها. في الناتج المنظم، افحص البنية والمفاتيح والقيم المطلوبة؛
لا يصلح اكتمال النقل دليلًا على صحة المعنى. وفي الشيفرة، تحقق بالأدوات والاختبارات المناسبة لديوان.
سجّل الإخفاق أو الانقطاع باسمه، ولا تحوّل جوابًا جزئيًا أو مجرد إنشاء وكيل إلى إنجاز.

٥. استخدم `task_update` للحالة و`task_complete` بعد تحقق معيار قبول **هذه البطاقة فقط**، ثم أعد قراءة
`task_status` للتأكد من حفظ النتيجة. افحص أخطاء JSON-RPC والأخطاء داخل محتوى الأداة؛ رمز HTTP الناجح وحده لا يكفي.
اختبار ربط مصطنع لا يغلق مسألة تطوير ولا يؤهل عاملًا للعمل المستقل.

٦. انقل النتيجة المقبولة إلى مرجع GitHub المناسب بدليل مختصر منقّح. لا تنشر سجل RuFlo الخام أو إعدادات الجهاز
أو بيانات محلية ضمن دليل عام. إن كان مخزن RuFlo زائلًا، فأعد بناء البطاقات من المراجع المعتمدة بعد فحص التكرار.

## إثبات المحلية وسقف الإنفاق

اسم النموذج أو وصف أداة مثل `agent_execute` لا يثبت أين ينفّذ النداء. قبل استعمال طريق جديد افحص شيفرة التوجيه
وإعداد العملية التي تنفذه: عنوان المزوّد الفعلي، وترتيب اختيار المزوّدين، والنموذج، ومسارات إعادة المحاولة.
لا تفترض أن إعداد واجهة المحادثة يضبط أيضًا أداة تنفيذ الوكيل؛ قد يكون لكل منهما طريق مختلف.

للتشغيل المحلي، تحقق من أن النموذج محلي فعلًا وأن النداء يذهب إلى خدمة محلية معلومة، وأن الفشل يُعاد للمستدعي
دون انتقال إلى خدمة مدفوعة. لا تُظهر المفاتيح أو البيئة كاملة أثناء الفحص. إن تعذّر إثبات الطريق فتوقف عند
تتبع البطاقة أو ارفض النداء بسبب مسمّى، بدل تجربة مزوّد غير معلوم التكلفة.

تخضع الواجهات السحابية لقرارات ديوان وقائمة المزوّدين المعتمدة. عند اشتراط المجاني فقط يكون السقف صفرًا،
ولا يُسمح بتجاوز الحصة إلى مسار مدفوع. سجّل النموذج والرموز وحالة النداء وأساس حساب التكلفة، ولو كانت صفرًا؛
التشغيل المحلي بلا رسم API لا يعني انعدام تكلفة الجهاز والكهرباء.

## حدود الوثيقة

هذه وصفة تنسيق عامة، وليست تقريرًا عن جهاز أو إثباتًا لتركيب خدمة أو نجاح تشغيل حي.
تختلف أدوات RuFlo وإعدادات التخزين والتوجيه بحسب النسخة؛ يُعاد فحصها قبل الاستخدام، وتبقى نتيجة العمل
ومعايير قبولها أهم من عدد الوكلاء أو ظهور لوحة التحكم بحالة سليمة.
